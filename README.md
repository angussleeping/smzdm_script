## ⚠️ 关于评论被永久封禁

### 结论

评论权限的永久封禁是**账号维度**的处罚，记录在 `smzdm_id` 上。更换 Cookie、更换抓包设备、重装 App 都不会解除。脚本无法解封，只能通过官方渠道申诉：

* App 内「我的 → 客服 / 意见反馈」提交申诉，说明是本人操作、已停止使用第三方工具、请求恢复评论权限；
* 申诉结果由平台判定，存在不通过的可能，这一点无法通过改代码绕过。

本版脚本能做的是**不再重复导致封禁的行为**，避免其他账号或解封后的账号再次踩同一个坑。

### 上一版为什么会踩线

根据被移除的 `smzdm_all.js` 及 `library_task.js` 的实际行为，评论流程同时具备三个高危特征：

| # | 行为 | 在代码中的位置 | 风险性质 |
|---|---|---|---|
| 1 | 发表评论后 20–30 秒调用 `delete_comment` 删除，删除率接近 100% | `doCommentTask` 中 `this.$env.log('删除评论')` 之后 | 发完即删是最直接的机器特征，真实用户不会这样操作；删不删服务端都有完整记录 |
| 2 | 遇到「发布 N 条评论」任务时循环补发，上限 15 条，每条落在不同文章 | 整合版 `doCommentTask` 的 `while (!result.isSuccess ...)` 循环 | 单账号在数分钟内跨多篇文章连续评论，是灌水识别的核心特征 |
| 3 | 文案池用尽后给原文案追加 1–9 个句号生成「变体」，用于规避重复内容检测 | 整合版 `getCommentContent()` | 近重复文本对 n-gram / 相似度去重无效，且「刻意规避去重」本身加重判定 |

三者叠加，再加上文案与文章内容无关、评论前几乎没有停留，整体行为与真实用户完全不符。这是本次封禁在代码层面最可能的原因（平台未返回具体判定依据，此项为基于行为特征的推断）。

需要说明的是：**其中第 2、3 项是本仓库上一版相对原版新增的「增强」**，并非原作者的实现。这类为了「把任务做完」而突破平台限制的改动，收益是几枚碎银，代价是账号的评论权限。

### 本版的改动

评论相关逻辑整体抽到 `library_comment.js`，默认关闭，开启后按最保守的节奏执行：

* **不再删除评论**。发表后保留，删除行为全部移除；
* **每日硬配额**。每账号每天最多 2 条，可下调，硬上限 3 条；
* **单次运行最多 1 条**。同一账号两次评论至少间隔 30 分钟，间隔与额度写入状态文件，跨运行生效；
* **「发布 N 条评论」且 N > 1 的任务一律跳过**，提示到 App 内手动完成，不再自动补发；
* **文案不再生成变体**。近期用过的文案直接跳过，池子空了就停，日志提示补充新文案；
* **评论前先停留阅读**。按任务要求的浏览时长，或默认 25 秒（`SMZDM_COMMENT_READ_SECONDS` 可调）；
* **文案支持 `{title}` 占位符**，用文章标题拼进评论，让内容与文章相关；
* **识别封禁响应**。接口一旦返回禁言/权限受限类提示，立即停止本次所有评论动作，不做重试。

代价是评论类任务大概率完不成，领不到那部分奖励。这是有意的取舍：评论任务的收益远小于失去评论权限的损失。

## 脚本内容

四个脚本独立运行，各自一个定时任务，互不影响：

| 脚本 | 功能 | 建议 cron |
|---|---|---|
| `smzdm_checkin.js` | 每日签到、连签奖励、金币/碎银/值会员信息 | `10 8 * * *` |
| `smzdm_lottery.js` | 每日抽奖（会员中心转盘） | `20 8 * * *` |
| `smzdm_task.js` | 每日任务（签到页任务，含浏览/收藏/点赞/评论/分享/抽奖/关注/站外浏览/推送等） | `20 14 * * *` |
| `smzdm_testing.js` | 全民众测能量值任务（需 `SMZDM_TASK_TESTING=yes` 才运行） | `20 15 * * *` |

公共库：`env.js`、`bot.js`、`library_task.js`、`library_comment.js`、`sendNotify.js`，必须与脚本放在同一目录。

> 上一版的整合脚本 `smzdm_all.js` 已从仓库移除。如果你已通过拉库更新，面板里旧的 `smzdm_all` 定时任务需要手动删除，否则会继续执行旧逻辑。

## 使用方法

### 青龙拉库

```bash
ql repo https://github.com/angussleeping/smzdm_script.git "smzdm_" "" "env.js|bot.js|sendNotify.js|library_" "main"
```

拉库后到面板「定时任务」里确认四个脚本都在，并按上表的 cron 分别为每个脚本建任务（拉库生成的任务可能需要手动启用或调整时间）。

### 手动部署

把四个 `smzdm_*.js` 与五个公共库放在同一目录（建议独立子目录，如 `smzdm/`），添加定时任务：

```bash
task smzdm/smzdm_checkin.js
task smzdm/smzdm_lottery.js
task smzdm/smzdm_task.js
task smzdm/smzdm_testing.js
```

### NodeJS 依赖

* got@11
* crypto-js

青龙面板「依赖管理 → NodeJS」里添加 `got@11` 与 `crypto-js` 即可。

### 抓包

建议使用 Android 手机抓包（iOS 也可以），域名为 `user-api.smzdm.com` 的任意链接，把**所有** Cookie 取出来放到 `SMZDM_COOKIE` 环境变量中，多用户请添加多个同名环境变量或用 `&` 符号分隔。

如果手机实在抓不到，也可以用浏览器的 Cookie，但强烈建议使用手机端的 Cookie。脚本会自动检查 `device_id`、`device_rid`、`z_dr` 等设备字段，缺失时在日志里提示，缺字段的 Cookie 更容易被风控。

### 环境变量

环境变量请使用面板的环境变量列表直接添加，不要用 `export xxx=""` 这种方式。

#### 基础

| 变量 | 必填 | 说明 |
|---|---|---|
| `SMZDM_COOKIE` | 是 | 抓包获得的完整 Cookie，多账号用 `&` 分隔，或添加多个同名变量 |
| `SMZDM_SK` | 否 | 签到请求的设备签名，从 Android App 的 `https://user-api.smzdm.com/checkin` 请求参数中抓包得到。多账号用 `&` 分隔，顺序须与 `SMZDM_COOKIE` 一致 |
| `SMZDM_USER_AGENT_APP` | 否 | App 的 User-Agent，从 App API 请求头抓包，建议用 Android 的 |
| `SMZDM_USER_AGENT_WEB` | 否 | App 内网页的 User-Agent，一般在转盘网页中抓包 |
| `SMZDM_CROWD_SILVER_5` | 否 | 设为 `yes` 时进行 5 碎银子抽奖。只有当日无免费抽奖时才执行 |
| `SMZDM_CROWD_KEYWORD` | 否 | 碎银子抽奖关键词，命中优先，未命中随机选 |
| `SMZDM_TASK_TESTING` | 否 | 设为 `yes` 才运行全民众测能量值任务 |
| `SMZDM_DEBUG` | 否 | 开启请求调试输出 |

关于 `SMZDM_SK`：不填时脚本会按账号派生一个固定的设备串来生成 sk（跨运行不变，但与真机的设备串不同）；填了之后会解密校验它是否属于对应 Cookie，不属于会在日志提示（通常是多账号顺序错位）。两种情况脚本都会把 Cookie 的 `device_rid`/`device_s` 对齐成 `md5(实际使用的设备串)`，并在缺 `z_dr` 时按 App 行为补齐。

#### 评论（默认关闭）

| 变量 | 默认 | 说明 |
|---|---|---|
| `SMZDM_COMMENT_ENABLE` | 未设置 = 关闭 | 必须设为 `yes` 才会执行评论任务。**不建议开启**，详见上方封禁说明 |
| `SMZDM_COMMENT` | 空 | 评论文案，多条用换行或 `\|` 分隔，每条须大于 10 个汉字。建议在文案中写 `{title}` 占位符，脚本会替换成文章标题，例：`关于{title}的总结挺实在，正好在挑同类产品，受教了` |
| `SMZDM_COMMENT_DAILY_LIMIT` | `2` | 每账号每日评论上限，硬上限 3 |
| `SMZDM_COMMENT_READ_SECONDS` | `25` | 评论前在文章页停留的秒数，范围 15–120 |

只在同时满足以下条件时才会真正发表评论：`SMZDM_COMMENT_ENABLE=yes`、`SMZDM_COMMENT` 至少有一条可用文案、当日额度未用完、距上一条评论已超过 30 分钟、且任务要求的条数为 1。

## 已知限制

* 发布笔记（`publish.biji_new`）、发布原创长文（`publish.yuanchuang_new`）、申请众测（`guide.apply_zhongce`）等任务需要人工创作或申请，脚本跳过并在日志提示
* 领取任务奖励时若被要求人机验证（`110202`），脚本无法通过，日志会提示到 App 内手动领取
* 转盘抽奖活动由官方运营，活动过期时日志提示「活动已过期」属正常现象
* 「发布 N 条评论」任务（N > 1）一律跳过，需手动完成
* 众测接口被 WAF 拦截时会跳过众测任务，不影响其他功能

## 风控提示

除评论外，以下行为在代码层面同样具备较强的机器特征，属于已知风险，本版不做进一步对抗性优化：

* 点赞任务中的 `like_create` / `like_cancel` 反复交替（为让计数生效而做的先取消后创建）
* 收藏、关注、关注栏目/品牌任务中的「先取消再创建再取消」
* 固定 cron 时间、固定请求间隔、固定 User-Agent
